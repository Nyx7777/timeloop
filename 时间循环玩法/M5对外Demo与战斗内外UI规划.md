## 1. M5 目标

M5 不只是增加几场战斗，而是把已经验证的战斗纵向切片组织成一段可以交给陌生玩家、无需开发者讲解的完整产品体验。

对外 Demo 的完整闭环为：

`标题/继续 → 本轮准备 → 路线地图 → 节点详情 → 战斗 → 战后结算 → 奖励/Build 选择 → 返回地图 → 事件/资源节点 → Boss → 本轮总结/合并回放`

本阶段同时解决两类缺口：

1. 战斗内：把 M4 已验证的交互骨架升级为正式 UI，并补齐固定敌人意图、扰动与清醒的信息表达。
2. 战斗外：建立路线、节点、奖励、Build、事件、Boss 和本轮结算组成的最小闭环。

M4 保持“已验收结项”。M5.0 是对既有战斗表现的产品化，不回滚 M4 的规则、动画和布局成果。

## 2. 统一 UI 设计系统

战斗内外界面共用同一套视觉语言，避免先分别制作、再被迫返工统一：

- 字体层级：标题、关键数值、正文、辅助说明与警告文字。
- 面板体系：顶部栏、普通卡片、弹窗、节点详情、奖励卡和 Boss 信息条。
- 图标体系：时间线、命数、回合、固定历史、扰动、清醒、奖励和资源。
- 按钮状态：默认、按下、选中、禁用、锁定、教程聚焦。
- 颜色语义：青色代表本体与可操作，紫色代表分身与录像，橙色代表固定历史，红色代表伤害危险，金色代表清醒或脱离固定历史。
- 动效语义：普通交互、锁定、断裂、清醒、获得奖励和关卡完成使用不同节奏。
- 可访问性：重要信息不能只依赖颜色；同时使用轮廓、图标、文字或动态中的至少一种辅助编码。

## 3. 里程碑与验收门禁

### M5.0A：战斗 UI 产品化与共享视觉系统

目标：先确定可以扩展到战斗外页面的正式 UI 语言，再修改运行时界面。

交付物：

- 战斗顶部栏、行动序列、情境提示和底部四按钮的正式视觉规格。
- 完整按钮状态矩阵：默认、按下、选中、禁用、锁定、教程聚焦。
- 字体、面板、描边、色彩、图标和动效的首版共享 Token/组件表。
- 四张 390×844 代表状态稿：T1 未知时间、T2 全部固定、固定与清醒混合、Boss + Build 信息上限。
- 360×800、390×844、430×932 三种比例的布局检查。

门禁：四张代表状态稿经用户确认后，才批量制作 UI 素材并接入 Godot；现有按钮和顶部栏视为已验证布局中的原型皮肤，不作为最终发布美术。

### M5.0B：固定意图、扰动与清醒信息系统

目标：让玩家在不读日志的情况下，快速理解每个敌人的时间状态及本回合行为。

固定敌人显示：

- 每名敌人拥有稳定编号，如 E1、E2，并与行动序列头像一一对应。
- 棋盘显示从敌人当前位置出发的橙色虚线路径、移动终点标记，以及从移动后终点发出的红色攻击线/危险格与伤害信息。
- 固定等待行为使用沙漏或“等待”标记，不能表现成无信息。
- 固定历史使用完整时钟徽记；多个意图重叠时，点击行动序列中的敌人头像可单独聚焦该敌人，其余意图降低透明度。

扰动与清醒分三段表达：

1. 扰动发生瞬间：播放断裂时钟波纹；显示“已扰动·本回合行为仍已锁定”。
2. 当前回合剩余阶段：保留该敌人的既定意图，并显示“下回合清醒”过渡徽记，避免玩家误以为当前行动已改变。
3. 下一回合起：敌人改用金色断钟/清醒状态，行动序列使用特殊边框；不再显示固定意图，棋盘以 `?` 表示其将在玩家行动后按实际战场重新决策。

顶部状态不再只显示全局“已知/未知”，而是提供类似“固定 2 · 清醒 1”的简洁汇总。规则语义保持不变：扰动不改变本回合已锁定行为；敌人下一回合清醒，在当前时间线持续实时决策，时间线结束后把新行为写入固定历史。

### M5.0C：接入与战斗可读性验证

目标：将 M5.0A/B 的正式方案接入现有六关，并验证复杂状态仍然清楚。

验收标准：

- 不查看日志，玩家可在 2—3 秒内指出每名固定敌人本回合将移动到哪里、攻击哪里。
- 玩家能指出哪个敌人已扰动、它本回合是否仍执行旧意图，以及从哪一回合开始清醒。
- T1 未知、T2 全固定、固定/清醒混合、等待、路径交叉和 Boss 信息上限均有覆盖。
- 360×800、390×844、430×932 无裁切、误触和关键遮挡。
- 六关可玩，现有 180 项核心测试与 92 项界面/动画测试不得回退；新增状态需加入表现回归。

### M5.1：战斗外 UX 流程与页面规格

先做低成本流程图和线框，再生产正式美术。覆盖：

- 标题/继续与新游戏。
- 本轮准备或最小战前配置。
- 路线地图、节点状态和节点详情。
- 战斗结果、奖励/Build 选择与返回地图。
- 事件/资源节点。
- Boss 进入提示。
- 本轮成功/失败总结与合并回放入口。

门禁：所有页面能串成可点击流程，返回路径、取消路径和失败路径明确；战斗外 UI 必须复用 M5.0A 的组件语言。

### M5.2：RunSession 与数据骨架

建立一轮游戏的唯一权威状态，至少包含：

- 路线图、当前节点、已访问/可访问节点和节点结果。
- 当前 Build、背包/资源、坍缩值与待领取奖励。
- 战斗开始前的输入和战斗结束后的结算输出。
- 可序列化的本轮状态，为继续游戏、失败恢复和测试复现留接口。

此阶段先确定数据与页面的边界，不提前搭建完整商店、Meta 或多章节框架。

### M5.3：最小宏观闭环

实现并打通：

`路线选择 → 节点进入 → 战斗 → 战后结算 → 奖励选择 → 返回路线 → 事件/资源节点 → Boss`

验收以一轮连续游玩为准，不再依靠开发菜单手工跳关来模拟产品流程。

### M5.4：首个对外 Demo 内容

推荐首轮规模为 6 节点左右：

- 1 个开始/教学节点。
- 2 个形成路线选择的普通战节点。
- 1 个事件或资源节点。
- 1 个汇合后的普通战或精英节点，用于检验 Build 成型后的战斗。
- 1 个 Boss 节点。
- 贯穿流程的 3—5 个奖励/强化选择，以及通关后的合并回放。

第一版原则上延期：完整商店经济、动态追兵、Meta 成长、多章节内容。第二种武器、监视、坍缩的完整玩法效果和合并回放的深度，在 M5.1 前按体验目标再次裁决；其中监视当前仍倾向不进入首版。

### M5.5：无讲解对外验证

- 邀请未接触项目的玩家从标题页开始独立完成体验。
- 观察是否能理解路线目标、奖励选择、时间循环、固定意图、扰动清醒、失败代价和最终目标。
- 记录完成率、卡住位置、错误理解、单次时长和是否愿意继续玩。
- 只根据高频理解问题和阻断问题调整，不在测试中临时扩张范围。

## 4. 开工前仍需确认的范围项

这些问题不会阻止 M5.0A 开始，但必须在进入 M5.1/M5.2 前确认：

- 对外测试对象、发布形式和目标单次时长；当前建议按 20—30 分钟规划。
- 首轮路线图的精确节点数量与分支结构。
- 最小 Build 的构成，以及奖励是否只做战斗强化。
- 坍缩值在路线层的表现与第一版实际作用。
- 第二种武器、监视、完整合并回放分别进入首版还是后续版本。

## 5. 当前开工顺序

下一轮只启动 M5.0A：

1. 盘点现有顶部栏、行动序列、按钮、弹窗和战术标记，区分可复用结构与原型皮肤。
2. 建立共享 UI 组件与状态矩阵。
3. 完成四张代表状态稿及三种竖屏比例检查。
4. 用户评审通过后进入 M5.0B 的意图/清醒细化与运行时实现。
